SLIDE 05 — How do we build mlir dsl?
PDF page: 6
Owner: Guray Ozen
Clock: 03:35–04:00
Target duration: 00:25

Ask the design questions before introducing the solution. MLIR is compiler infrastructure, not one fixed end-to-end compiler. Compiler A and B may choose unrelated dialects and lowering pipelines. Control-flow models also differ: a direct scf.for has no break operation, while scf.while can express termination and another dialect may model early exits differently. We need to reuse frontend infrastructure without hard-wiring these target decisions.

PDF page: 7
Owner: Guray Ozen
Clock: 04:00–04:20
Target duration: 00:20

The core owns reusable orchestration and language policy. The four boxes are services, not plugin kinds. BaseDSL begins with an empty Plugins record: it supplies no default target dialect or compiler and is not by itself an end-to-end language. SLIDE 09 — How much Python should we implement?
PDF page: 10
Owner: Guray Ozen
Clock: 05:10–05:45
Target duration: 00:35

Compare ownership, not absolute expressive power. A broad AST-based frontend interprets or lowers supported Python constructs and owns those semantics; it can target many dialects. This design chooses tracing to reuse the interpreter for objects, imports, method dispatch and metaprogramming. Plugins supply the target operations. Tracing alone does not intercept native staged if/for/while; optional limited AST capture handles that syntax. The following design principles and multi-stage slides explain the resulting model.
