3. COMPILATION/LAUNCH POLICY IS NOT FIXED TO PYTHON -> JIT -> KERNEL
Default familiar CuTe call story: Python -> @jit host metaprogram -> @kernel launch.
Shared decorators route to _func / _kernel_helper (base_dsl/dsl.py:769–802).
Nested @jit calls while a trace is active inline their Python bodies, with PyIR context handling (base_dsl/dsl.py:3213ff). Do not promise automatic separate runtime func.call for every decorated helper.

A direct Python -> @kernel path ALREADY EXISTS in CUDA Tile:
- CudaTileIR constructor sets device_compilation_only=True (cuda_tile.py:635).
- Its jit override explicitly says use @CudaTileIR.kernel and call the GPU kernel directly (:706).
- _kernel_helper (:1009) selects backend and target-specific kernel generator.
- _backends.py:78 _make_kernel_generator uses inherited kernel_launcher and a target helper.
- _backends.py:147 launch_gpu chooses grid=num_tiles, block=(1,1,1), and calls base _execute_by_cuda_driver.
- base_dsl/dsl.py:3331 _execute_cuda loads cubin, gets function, resolves stream, launches, optionally synchronizes; :3371 _execute_by_cuda_driver generates IR, compiles cubin, executes.
Thus “a direct launcher remains to implement” undersells DKG. Correct framing: “Extract the existing device-only path; a sub-DSL chooses its runtime adapter.” If showing modern CUDA Python ObjectCode APIs as a cleaned adapter, label that particular code as the proposed replacement for current runtime helpers, not the existence of direct launch itself.

Target coupling to move OUT of the neutral BaseDSL:
- CUDA helper imports and _execute_cuda (rather than deleting its functionality).
- SM-specific option name `pass_sm_arch_name` -> generic target/pipeline option object.
- gpu_module naming and func/gpu/CUDA-specific builder choices -> module/entry builder hooks.
- default GPU adapter scopes -> explicit sub-DSL choice.
- CUDA-specific compile options/backends and binary formats -> target plugin/provider.
- CuTe naming and environment enum logic -> downstream policy.
Retain common scheduling of trace -> hash/cache -> compile -> artifact -> execute.

Inference remains local: definition-site DSL annotations, wrapped IR types, operand promotion, result wrapping. Scalar i32/f32 types are builtin MLIR types; arith supplies the operations. Use that technically accurate phrasing.

Replacing arithmetic policy:
DKG has a clean conceptual separation Numeric/promotion -> ArithValue/emission, but there is NOT already a declarative arithmetic plugin parameter to NumericMeta. IntegerMeta/FloatMeta docstrings mention arith fields, yet actual constructors have no `arith=` parameter. Do not invent it as existing.
For extraction, two grounded choices:
1. Downstream wrapper Tensor/Tile overloads Python operators to emit its own dialect. Already demonstrated by CUDA Tile binding value wrappers.
2. Expose an arithmetic-emitter policy at the Numeric -> ArithValue boundary. This is target design/refactoring work; name it as such. It directly addresses requested “plug your arithmetic” slide without treating prototype limitation as the goal.
Suggested slide diagram: Python `x + y` -> promotion policy -> [default arith emitter | yourdialect emitter]. Notes: default implementation extracted from DKG ArithValue; alternate emitter is the new extension hook.

5. TYPE EXTENSION IS AN EXISTING PROTOCOL, NOT ONLY PROTOTYPE register_leaf
base_dsl/typing.py:77 DynamicExpression protocol:
    __extract_mlir_values__(self) -> list[ir.Value]
    __new_from_mlir_values__(self, values) -> object
Purpose: user-defined objects cross JIT helper calls, returns and staged control-flow regions.
base_dsl/typing.py:148 JitArgument protocol adds:
    __c_pointers__(self) -> list[ctypes.c_void_p]
    __get_mlir_types__(self) -> list[ir.Type]
    __new_from_mlir_values__(self, values) -> object
Purpose: host argument ABI plus reconstruction from function block args.
runtime/jit_arg_adapters.py provides scoped host-object adaptation.

Small DKG-grounded downstream type snippet:
    class Tensor:
        def __init__(self, value):
            self.value = value
        def __extract_mlir_values__(self):
            return [self.value]
        def __new_from_mlir_values__(self, values):
            return Tensor(values[0])
        def __add__(self, rhs):
            return Tensor(mydialect.add(self.value, rhs.value))
The mydialect op spelling is illustrative. The extract/rebuild methods are exact existing protocol. Host tensor import additionally needs JitArgument/adapter, not just this SSA protocol.
Extraction may expose the prototype's register_leaf callbacks as an alternate registration convenience, but explain equivalence to existing DKG protocols. Do not imply custom types are a hypothetical future capability.
