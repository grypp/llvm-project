Naming and architecture
-----------------------
Installed core: mlir.dsl. Reference e2e namespace: import mlir.mlir_dsl as m.
Reference class: MlirTestDSL; it subclasses BaseDSL and names one Plugins record.
BaseDSL.plugins = Plugins() is empty. The core imports no dialect or plugin.
It supplies @jit, argument staging, type policy/value model, shared tracing,
cache orchestration, diagnostics, environment management, and extension contracts.
Types/operator emission, entry construction, AST rewriting, compilation and extra
decorators/adapters are selected by the sub-DSL. The core is not an e2e language.

A plugin is a component implementing one named extension contract in Plugins.
Four single-valued ROLES (at most one plugin per role):
  type_ops -> TypeOpsPlugin -> OpEmitter type/operator hooks.
  func_entry -> FuncEntryPlugin -> generate_func_op, generate_return,
                pack_results, unpack_result.
  ast_preprocessor -> ASTPreprocessorPlugin -> preprocessor_class,
                      closure_check, executors(dsl).
  compiler -> CompilerPlugin -> compile, jit, compile_and_jit, load,
              remark_session, print_ir_after_passes.
Two multi-valued FAMILIES (zero or more each):
  decorators -> DecoratorPlugin -> decorators(dsl_cls), before_trace,
                after_trace, check_arguments, finish_compiled_function.
  adapters -> AdapterPlugin -> register(dsl), attach_to_module,
              after_lowering, wrap_compiled_function.
Eight shipped plugins:
  TypeOps, func.Entry, scf.ASTPreprocessor, execution_engine.Compiler,
  gpu.Kernels, PyTorchPlugin, DlpackPlugin, TvmFfiPlugin.
TypeOps(scalars=arith, vectors=vector, memory=llvm) is ONE plugin.
arith/vector/llvm are op modules beside it, not separate plugins.
Every group of TypeOps is optional. An omitted group diagnoses when used.

Plugin base only shares available(), install(dsl), shared_libs(),
register_dialects(ctx). BaseDSL resolves record once per concrete singleton
instance; unavailable optional components are dropped and listed in
unavailable_plugins; remaining components are shallow-copied and installed in
record order. An untyped bare Plugin cannot be placed into any Plugins field.

The sub-DSL, not its plugins, owns pipeline(). No plugin contributes passes.
BaseDSL.pipeline() is []; pipeline= call keyword or <PREFIX>_PIPELINE overrides.
The reference class explicitly lists the upstream-to-LLVM passes and optionally
the GPU pipeline when ARCH is set. register_dialects(ctx) is also a sub-DSL hook;
plugins may register their own dialects via their lifecycle hook.

Concrete class setup, no reference-DSL dependency
-------------------------------------------------
The following is a source-correct CPU DSL for scalar expressions. Keep the long
imports/pipeline in speaker notes if visible code needs to stay short. A native
control-flow DSL additionally names scf.ASTPreprocessor(), sets preprocess=True
and exports the preprocessor helpers through its own dsl_package_name namespace.

from mlir.dsl import BaseDSL, Plugins, Int32
from mlir.dsl.plugins.type_ops import TypeOps, arith
from mlir.dsl.plugins.func_entry import func
from mlir.dsl.plugins.compiler import execution_engine

class MyDSL(BaseDSL):
    plugins = Plugins(
        type_ops=TypeOps(scalars=arith),
        func_entry=func.Entry(),
        compiler=execution_engine.Compiler(),
    )

    def __init__(self):
        super().__init__(name="MY_DSL", preprocess=False)

    def pipeline(self):
        return ["convert-arith-to-llvm", "convert-func-to-llvm",
                "reconcile-unrealized-casts"]

@MyDSL.jit
def add(a: Int32, b: Int32):
    return a + b

Tracing, Meta and runtime values
-------------------------------
Python evaluates ordinary objects/imports/classes/dicts/polymorphism while
tracing. A Numeric holds .value: a Python literal or an ir.Value; its .dtype is
its class. Both operands with Python payload fold through Python's operator.
A staged operand makes the type-ops plugin materialize constants and emit IR.
The active BaseDSL.is_mlir_op judges leaves; public is_mlir_op recursively walks
tuples, lists and frozen records. Dicts and arbitrary objects remain Python.

IMPORTANT documentation nuance: README says annotations alone decide staging,
but executable is_argument_meta explicitly also inspects contains_leaf(arg).
A plain unannotated int/float/bool is Meta. A DSL annotation selects a runtime
argument. An adapted registered-leaf value can stage even without annotation.
A reserved receiver, type argument or None is Meta. Plain int annotation is
Meta, not equivalent to Int32. There is no Constexpr marker.

Python tracing is the selected approach, with optional AST capture for native
staged if/for/while. Do not say the implementation contains no AST pass.
The accurate design argument is that Python semantics/metaprogramming need not
be reimplemented per target: types and operations dispatch through plugins;
restricted syntax capture handles keywords Python cannot proxy-overload.
It is not a general theorem that an AST-based frontend cannot target many
dialects. Present this as the tutorial's scaling/design choice.

Sources: dsl/core/staging.py; dsl/types/typing.py; dsl/core/mlir_op.py;
         sub-dsls/mlir-dsl/examples/01_staging.py.

Type system and conversions
---------------------------
Classes carry width/signedness/type properties. Numeric carries Python or SSA
payload, not a separate runtime annotation wrapper.
Literal defaults when entering typed expressions:
  bool -> Boolean; int -> Int32, or Int64 outside signed i32 range;
  float -> Float32. Plugin decides the actual MLIR representation.
Int32.scalar_mlir_type is the underlying scalar i32;
Int32.mlir_type consults the active DSL type_ops and requires an active trace.
A plugin instance can answer its mlir_type(Int32) outside a trace.

Promotion is common Python policy before op emission:
  same types stay the same; same signedness integers choose wider;
  mixed signedness chooses unsigned when width >= signed width, otherwise signed;
  floats choose the supported common width; Float16 beats BFloat16 at equal width,
  Float32 beats TFloat32; unsupported mixed narrow formats diagnose and require
  an explicit conversion. Comparisons produce Boolean.
Use examples Int16+Int32 -> Int32 and Int32+Float32 -> Float32.

x.to(m.Float32), m.Float32(x), m.cast(x,m.Float32) convert explicitly.
Staged operands emit type-ops cast operations. Python payloads fold.
Narrowing is supported, not always an error. Explicit integer literals can wrap;
out-of-range magnitude warns. Runtime -> int/float/bool raises
PHASE_REQUIRES_CONSTANT. Distinguish unsupported promotion errors from explicit
narrowing warnings and invalid host annotation errors.
Core type families: signed Int2..Int128, Uint8..Uint128, Boolean; Float16/32/64,
BFloat16/TFloat32; fp8/fp6/fp4 variants. Availability of a type does not promise
that every backend/host ABI supports it.

Extending a downstream Tensor value model
----------------------------------------
register_leaf records a class once at module import. The class may hold raw
ir.Value in ordinary fields; no prohibited annotation wrappers are needed.
Illustrative staged-only implementation excerpt:

class Tensor:
    def __init__(self, value):
        self.value = value

register_leaf(
    Tensor,
    ir_types=lambda x: [x.value.type],
    ir_values=lambda x: [x.value],
    from_ir_values=lambda prototype, values: Tensor(values[0]),
)

This lets a downstream dialect's result participate in calls/region carries.
It does not define Tensor arithmetic, create that dialect's ops, or marshal a
host tensor; those are separate behavior/adapters. A host boundary requires a
marshal function, and an annotation may need a richer type/prototype contract.
Frozen dataclasses/structs flatten fields; @struct is NOT an LLVM SSA aggregate.
Reference leaves mark Pointer as reference=True so memory stores don't force
an SSA carry, unless the pointer name is rebound.
Sources: dsl/util/tree_utils.py; test/helpers.py (Pair leaf example).

Control flow
------------
scf.ASTPreprocessor owns both the rewrite and executors selecting SCF regions.
There is no separate SCF dialect plugin. Explicit builders are in
plugins/ast_preprocessor/scf/builders.py and reference namespace re-exports them.
Native for/if/while, ternaries, comparisons and supported bool/builtin functions
route on staged operands. Meta control flow remains Python. Bare range with
Python bounds executes at trace time; m.range explicitly stages.
Assignment analysis identifies carried names; executors flatten/rebuild values
and emit iter_args/yields. Frozen records work; unsupported mutable captured
state diagnoses. Closures inside staged regions are rejected by default;
scf.ASTPreprocessor(closure_check=False) is an explicit option.

A custom AST plugin can replace preprocessor_class and executors(dsl).
Current mapping keys are loop_execute_range_dynamic, if_dynamic, while_dynamic,
compare_executor, builtin_redirector, ifexp_dynamic.
The old is_dynamic_expression executor key is gone; use is_mlir_op predicate.
First-listed-AST-plugin semantics no longer apply: exactly one ast_preprocessor
role in Plugins. Preprocess can be bypassed by @jit(preprocess=False) or env.
A staged early exit still diagnoses; don't state MLIR scf.while itself cannot
express early termination. Those are frontend restrictions, not all of MLIR.

Compilation, host boundary, caching
----------------------------------
Host entry plugin func.Entry builds func.func + C interface, pack/unpack results.
No core host_entry='llvm' switch. CompilerPlugin owns lowering AND invocation.
Reference execution_engine.Compiler runs pass manager + ExecutionEngine + packed
ctypes calls. A DSL with no compiler traces only and returns traced result;
explicit compile_only without compiler diagnoses. DRYRUN also traces only.
No compiler does not mean no type_ops/func_entry: IR generation still needs the
roles for the values and entry it emits. PRINT_IR displays it; KEEP_IR retains it.

import mlir.mlir_dsl as m
@m.jit
def add(a: m.Int32, b: m.Int32):
    return a + b
compiled = m.compile(add, 5, 7)  # trace/lower/JIT, do not execute
result = compiled(8, 9)          # 17

This is compilation ahead of the call, not an object-file AOT export API.
No bracketed flags syntax. compile_only bypasses normal memory-cache retention.
Call parameters include pipeline, extra_link_libs, container_attrs, no_cache.

NumPy arrays adapt in core. PyTorchPlugin adapts torch.Tensor through data_ptr,
dtype and device, keeping ownership with caller. DlpackPlugin adapts the protocol
through compiled TensorView extension. Both yield a contiguous Pointer; sizes
are explicit arguments. No m.Array/memref descriptor built by this implementation.
TvmFfiPlugin is outbound ABI wrapping; optional dependency must be installed.

Cache key: traced module bytecode + affects_compile environment settings +
pipeline + extra link libraries + toolchain identity. In-memory stores callable;
disk stores lowered MLIR bytecode with CRC32; file hit skips passes, still builds
engine. Do not promise that Python tracing is skipped: caching occurs after IR.
Sources: dsl/core/dsl.py, dsl/util/cache.py, dsl/core/arguments.py,
         plugins/compiler/execution_engine.py,
         plugins/adapters/pytorch/plugin.py, plugins/adapters/dlpack/plugin.py,
         sub-dsls/mlir-dsl/examples/09_compile_and_cache.py.

Kernels and LaunchConfig
------------------------
Core only knows @jit. gpu.Kernels in decorators adds @kernel. The generic kernel
plugin helper is itself a DecoratorPlugin template for downstream targets.

@m.kernel
def add_one(p: m.Pointer[m.Float32]):
    i = m.thread_idx()[0]
    p[i] = p[i] + 1.0

@m.jit
def run(p: m.Pointer[m.Float32]):
    add_one(p).launch(m.LaunchConfig(grid=[1], block=[32]))

LaunchConfig also supports keyword .launch(grid=[1], block=[32]); dimensions
pad to three. Generic GPU path requires launch inside @jit and device memory,
uses synchronous gpu.launch_func, and checks architecture/buffer kind. Non-empty
async_deps is rejected. m.kernel call alone only creates pending launcher.
No general direct Python->GPU-kernel e2e path in this shipped plugin.
Target custom decorator/compiler may choose a different launch model.
Sources: plugins/decorators/kernels/launch.py;
         plugins/decorators/kernels/gpu/__init__.py;
         sub-dsls/mlir-dsl/examples/12_gpu_kernels.py.

Diagnostics, remarks, observability
----------------------------------
User mistakes: DSLUserCodeError with DiagId, source frame/caret/suggestion.
Framework/configuration failures: DSLRuntimeError. Dialect plugin-specific
catalogues may define their own stable codes. Do not portray remarks as errors.
DEBUGINFO adds source/traceback locations; LOC_TRACEBACKS configures depth.
Compiler's remark_session spans trace and passes, default no-op without compiler.
MLIR_DSL_REMARKS='.*' enables matched remarks; POLICY all/final; OUTPUT .yaml or
.bitstream streams output; without OUTPUT records collect in collected_remarks.
Profiling/logging/cache/IR-print controls use each DSL's <PREFIX>_* environment.
Reference prefix MLIR_DSL; user prefix e.g. MY_DSL via BaseDSL(name=...).
